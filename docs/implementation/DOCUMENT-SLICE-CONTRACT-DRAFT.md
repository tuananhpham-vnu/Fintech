## 2. API, identity và nguồn

## 3. Storage operations và DB transaction boundary

Đề xuất backend A: object store có immutable version ID + create-if-absent và credentials không overwrite/delete accepted objects. B: dedicated local filesystem trên một host với exclusive create, atomic visibility, file+directory durability và read-only AI process. Chưa chọn vendor/filesystem layout. AI hiện nhận storage_key và đọc local root: object-store adapter cần **worker-owned verified private materialization** của exact version cho AI, không tự gửi arbitrary remote URLs hoặc giả existing AI đã đọc object store. Đây là dependency thật trước S3.

Port dưới đây là **draft design**, không thêm vào shared runtime ports:

```typescript
type ExactObject = {
  opaqueObjectId: string
  storageVersion: string
  sha256: string
  byteLength: number
}
// All contexts/IDs come from an authorized backend intent, never client paths.
interface ImmutableStoreDraft {
  stageBounded(bytes: AsyncIterable<Uint8Array>, limits: ExplicitLimits): Promise<StagedCandidate>
  createIfAbsent(intent: AuthorizedIntent, candidate: StagedCandidate): Promise<ExactObject>
  headExact(object: ExactObject): Promise<VerifiedObjectMetadata>
  readExact(object: ExactObject): AsyncIterable<Uint8Array>
}
// Intentionally no overwrite/latest/unscopedRead/deleteAccepted method.
```

Do not hold a database transaction/row lock while uploading or calling AI/storage. Cross-resource atomicity needs an explicit saga; DB rollback alone cannot remove durable bytes. Proposed ordering:

1. **Receive/preflight:** authenticate+Origin+CSRF/ACL; bounded private staging/hash; real parser inspect before public accept, outside TX. No public document/job or incremented case revision yet.
2. **T-intent:** short TX rechecks session/ACL/revision/active quota/lineage or approved request; reserve unique scoped idempotency intent with digest/metadata/expected source snapshot and quota reservation. No accepted202/result yet. Concurrent in-flight does not create another intent. Schema/state/unique constraints need owner freeze + sole migration writer.
3. **Durable object:** outside TX, create-if-absent exact intent target. Matching object can finish same intent; different bytes/version under target fails conflict and quarantines. Ambiguous provider outcome must head/read exact object before retry; never overwrite to “repair”. A staging-file rename alone is not durable acknowledgement.
4. **T-accept:** short TX rechecks current session/ACL/revision, reservation/target/request/quota and exact durable object metadata; inserts immutable document/version + queued job/outbox record, updates lineage pointer, increments case revision once, appends audit, stores frozen202, completes intent. Commit all or none. Only then send202. No full AI extraction in request TX. Initial claim/condition verification untouched.
5. Worker later reads committed jobs; a DB job table can itself be the durable queue (proposed); no Redis/BullMQ selection implied. If an external broker is selected, transactional outbox is required, not dual-write network publish inside T-accept.

## 4. Job, lease, retries và publication

Proposed public states follow FE `queued|running|completed|partial|failed`; lease/attempt/reconciliation state is internal and not a fake progress percentage. For initial extraction slice, completed means a valid extraction result has the approved publication outcome, not all fields verified/non-null. **Partial is reserved until a precise producer/outcome criterion is approved**, not inferred merely from diagnostics/null fields. Stale/not-current is publication metadata/derived state, not an invented replacement public job enum.

Proposed technical budgets for review, not configured now:lease30s, heartbeat10s, per-attempt deadline240s, max3attempts, total job budget900s; retry backoff1s/2s (cap10s, bounded jitter). DB clock controls lease, monotonic process budget controls local reads. Values must fit actual provider budget; heartbeat never extends total deadline.

## 5. AI boundary, raw capture và capabilities

## 7. Freeze và integration ownership

Owner approval must identify which P rows/slices are released, not generic “OK Phase2”. Lead then publishes machine contracts/examples/error/status vectors and versioned port. Persistence writer alone adds intent/document/job/source schema, tenant FKs, uniqueness and TX adapters; storage agent owns backend adapter; document agent owns API/domain; AI adapter agent owns raw/validated mapping; worker agent owns lease/publication **after** ports/schema. QA owns test harness/matrix. No two agents edit shared DTO/SQL.

Integration order: approved S1 contracts → migration/UoW/repositories → storage durability + new upload → replacement → source reads → approved job/AI binding + async extraction → response mode after request contract. B03/public proxy/security and real full stack are gates before public deployment; FHI/method remains a separate release. No code from this draft is permission to open writes now.
